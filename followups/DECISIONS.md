# Follow-ups batch: decisions log

Decisions made while running the four follow-ups (repo id vs add-on namespace, SKILL.md check at launch, revision `extends`, repo-library scoping), each with why.

## Process

- **D1. Branches.** The integration branch is `ccr-143df22f-uetbpy`, cut from main at f024b41. Each item is built in its own child session on its own branch (`ccr-143df22f-uetbpy-<n>-<slug>`) and lands as its own PR into the integration branch. One final PR goes from the integration branch to main. *Why:* the user asked for separate PRs and a single PR to main; this session's own branch is the integration branch, so no other branch is pushed by this session.
- **D2. Validation before merging a child PR.** CI (`.github/workflows/test.yml`) runs on every pull request whatever its base. Its `branches: [main]` filter applies only to `push`, which an earlier version of this note misread. So each child PR gets full CI, and CI must be green before this session merges it. Children also run the checks locally before pushing (`just lint`, `just intent`, `just check-tests`, the affected tests, and `just test-ui` when touching `frontend/`), so a red CI run is a surprise, not a discovery.
- **D3. Tooling.** `just` is not preinstalled in the cloud image. Children run `uv tool install rust-just` (verified to work), then `just setup`.
- **D4. Order.** Items 1–3 run in parallel from the start. Item 4 starts in parallel too, but merges the integration branch in once item 1 has landed, before its own PR is merged, because both touch repository ids as namespaces. Merge order into the integration branch: 1, 3, 2, 4 (smallest first). *Why:* parallelism, without 4 reworking 1's code twice.
- **D5. Merges into the integration branch** are done by this session after reviewing each child PR (a code review pass plus re-running the checks on the merged head). The final PR to main is opened but not merged: main's review gate (CI, Claude Approvals, the user) decides.
- **D14. Handing specs and plans to the children.** Specs and plans are not committed to the repo (CLAUDE.md), and they are too large to paste reliably into a session prompt (about 150 KB). They go on an orphan branch, `ccr-143df22f-uetbpy-handoff`, which holds only `followups/*.md`, shares no history with main, never gets a PR, and is deleted when the batch is done. Children read them with `git fetch origin ccr-143df22f-uetbpy-handoff && git show FETCH_HEAD:<file>`, and never commit them to their own branches.
- **D6. Release labels.** `pr-labels.yml` runs on every PR, whatever its base. Child PRs carry `release::none` (each rides with the final PR) and a `## Changelog` line the final PR collects. The final PR's label is decided once all four land.

## Cross-plan review (plans 1–4 read as a set)

- **D7. Who adds a cross-item test row: the item that merges later.** Order is 1, 3, 2, 4, so item 4 adds every row that needs another item's code (the revision naming another repo's library in the direct `extends` form, which needs item 3's `QualifiedIdentifier`; an edited own-repo library store at launch, which needs item 2's `edit_store` and `_launch_problem`). Item 2 re-runs item 3's revision and gate tests after merging. *Why:* the earlier item cannot see the later one's code; the later one can, and only it can write a test that fails without both.
- **D8. Every child merges `origin/ccr-143df22f-uetbpy` before opening its PR** (and again if a sibling lands while it is open), re-runs the sibling tests its plan's "Coordination" section names, and compares removals against the integration branch: `uv run python dev/check_removals.py origin/ccr-143df22f-uetbpy BODY.md`. *Why:* PR base is the integration branch (D1), so `origin/main` is the wrong base for removals, and a later item must build on what landed.
- **D9. Each child PR's `## Changelog` holds its one user-facing line even under `release::none`** (plans 1–3 had said "leave it empty"). *Why:* D6 says the final PR collects the children's lines; an empty section leaves nothing to collect.
- **D10. Revision functions take `repo_id: str | None = None`; `load.for_item` takes it as a required keyword.** None means "no repository": every repo library is out of scope, add-ons are untouched. So item 3's rows (add-ons only) stay valid because scope never touches an add-on, not because of the default; and every production caller passes the item's id, pinned by a route-level own-repo row in item 4. *Why:* resolves spec 4's two statements (fail closed vs. "valid because default None"); a required keyword on revise/render/artifact_digest/evaluate would churn about twenty test call sites for no extra safety, since the fail-closed default cannot leak.
- **D11. Line budgets (`dev/check_tests.py`, 800).** Files at or near the ceiling get no growth beyond what is stated: `tests/addons/test_update.py` 794 (item 2 +3 via a module constant, item 4 0: its row goes to a new `tests/addons/test_update_repo_ids.py`), `tests/api/test_deps.py` 800 and `tests/api/test_repos.py` 792 (no plan adds; item 4 uses `tests/api/test_deps_repo_library.py` and `tests/api/test_repos_library.py`), `tests/executor/test_dispatch.py` 896/898 and `tests/adapters/test_agent.py` 855/856 allowlisted (no plan adds; item 4's fan-out row goes in `tests/executor/test_dispatch_pins.py`), `tests/test_intake_poller.py` 786 (no plan adds). Shared files summed: `tests/addons/test_pins.py` 344 → ~510 (2: +15, 3: +45, 4: +110), `tests/addons/test_repo_library.py` 679 → ~750 (1: +8, 2: +15, 4: +45; item 4 moves its new test to `tests/addons/test_repo_library_scope.py` if `wc -l` would pass 790). *Why:* the budget is per file and the four items grow the same files; no allowlist entry may be added for a file under budget.
- **D12. Intent ids are unique across the batch** (checked against main): item 1 `a-minted-repository-id-skips-addon-namespaces`, `a-workspace-never-names-an-addon-namespace-id`; item 2 `an-edited-store-file-is-never-read`, `an-edited-store-is-replaced-not-reused`; item 3 `a-revision-can-add-an-addon-component`; item 4 `a-repo-library-is-visible-only-to-its-repository`, `a-repo-id-is-never-another-tools-plugin`. Repoints: item 1 `templates-v1.md` `…as_members` → `[own-name]`; item 4 `kraft-repo-libraries.md` `test_disconnect_is_refused_while_something_names_the_library` → `[its-own-schedule]`, `[a-hand-edit]`. No two items repoint the same pin. *Why:* a duplicate id or a pin to an uncollected test fails `just intent` on the merged integration branch.
- **D13. One launch-stop rule when items 2 and 4 meet.** Item 4's `resolve_agent_task` check raises with the left-out add-on's own `left_out` text (the scope message for another repo's library, item 2's digest message for an edited store), and `for_item` applies `scoped` before item 2's `_launch_problem`, so an out-of-scope store is never hashed. *Why:* otherwise an own-repo library with an edited `profiles.yaml` would be reported as "visible only to items in app", which is false.
